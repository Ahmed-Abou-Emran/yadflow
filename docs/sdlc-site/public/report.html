Yadflow — Terminology & Structure Report

Yadflow (yahd-flow — from يد, Arabic for “hand”) is shared project memory and workflows for teams building with AI: plans, decisions, contracts and reviews kept as versioned files, with a person approving every planning step. AI builds. The hand decides.
A plain-language guide to every term used in the project (npm + GitHub: yadflow), plus the full workflow structure with diagrams — including how to run it on a brand-new (greenfield) project, an existing (brownfield) project, and a multi-repo product.

1. The big picture — what Yadflow is

Yadflow is a team workflow engine (installed from npm as yadflow; the skills are named yad-* and the CLI command is yad). It takes a feature from a raw idea all the way to shipped code, in small steps. Every step does its work, writes its result to a plain file, and then stops and waits at a gate until a human approves. Nothing is hidden in a database — all state is files you can read and edit yourself.

The one-sentence idea: AI does the heavy lifting; humans keep every important decision. Automation is never assumed — the team switches it on per step, reading the run record, and it can be switched off in one move.

The handoff rule: everything up to and including the locked contract lives in the Product. Everything from the spec onward (specs, tasks, code) lives in each code repo, with a link back to its story.

The three parts

Shape = decide (the “brain”).
Runs once per epic, in the Product. Here the team agrees on the epic, the architecture, the locked contract, the UI design, and the stories. Every Shape review is always human-approved. An author step’s dial can be set to auto, but that is only recorded for now — nothing moves a Shape step on its own.
Build = build.
Runs once per story, per code repo, inside that code repo: spec → implement → check → ship. These are the safe, mechanical steps — the team can set them to run on their own.

The two dials (set per step)

DialValuesWhat it answers
Driver human · pair · agent Who does the work of this step — a person, a person and an agent together, or an agent?
Advance human · auto Who moves this step forward — a person or the machine?

Each dial is written under two names while the rename settles, and the OLDER one is still the one the engine reads: driver beside assistance (human=none, pair=review, agent=heavy) and advance beside automation (human=human_approve, auto=machine_advance). yad migrate adds the new names to an existing project.

Keeping the dials separate lets you say “an agent does the drafting, but a person must approve” — the exact setting for the design steps. Every step starts at advance: human, and the team changes a dial with yad dial. Only two kinds of step are always human: every review gate and the final engineer review. A Shape author step’s dial can be set to auto for the whole project (kept in .sdlc/automation.json), but nothing acts on it yet. A Build step on auto is moved on by the yad-run skill after a clean run.

3. The review gate — the same loop, everywhere

Every review in the workflow is the same loop, run by yad-review-gate. Commenting never advances anything. What moves the step forward depends on where the Product lives — and it moves only when the approval rule is met:

yadflow keeps no list of people and there are no roles. Anyone with access to the repository can approve, and the platform records who did (their login). Every review uses the same count rule: base 1 + the step's risk step.

4. Terminology glossary — every term, in plain language

Type to filter. Each term is tagged by area: core files & artifacts gates & review Build automation tools people & roles

Core concepts

SDLCcore
Software Development Life Cycle — the journey of a feature from idea to running code. This repo gives a team one shared, disciplined version of that journey.
State machinecore
The core design: the workflow is a fixed set of states (steps). Each state does its work and waits at a gate. The states never change — only the trigger (who moves work forward) changes. That is what lets the team start fully manual and automate gradually without rebuilding anything.
Product (product repo)core
The git repo that holds the shared “thinking”: epics, architecture, the contract, UI design, stories, reviews and all state. The brain of the project. Code never lives here.
Code repocore
A separate git repo holding real application code (e.g. backend, mobile, dashboard). Each story’s spec lives inside the code repo it belongs to, with a link back to the story in the Product.
Skills source (this repo)core
The yadflow repo itself — where the 38 skills live and where you pull updates from. No real product work happens inside it.
Shape (“decide” / the brain)core
The first half of the workflow, run once per epic in the Product: analysis (optional) → epic → architecture + contract → UI design → stories — each followed by a human review gate, ending at ready-for-build. Test cases is a parallel, non-blocking track that opens at the stories gate and runs alongside Build. Every Shape review is always human-approved.
Build / Build (“build”)core
The second half, run once per story per code repo, inside that repo: spec → implement → checks → PR → ship. The team may set these mechanical steps to run on their own.
Gatecore
A stopping point after a step. The step writes its output and waits; a human must approve before the workflow moves on. “Every step stops at a gate” is the heart of the whole system.
Driver dialcore
A per-step setting for who does the work: human (no AI), pair (a person and an agent together), or agent (the agent drafts, the person directs). Older name in the files: assistance — none, review, heavy.
Advance dialcore
A per-step setting for who moves the step forward: human (default — a person records the approval) or auto (the orchestrator moves on by itself). Older name in the files: automation — human_approve, machine_advance. A review gate and the engineer review can never be set to advance: auto. A Shape author step can be, but that is only recorded (in .sdlc/automation.json) — nothing acts on it yet.
End-first automationcore
The rule for which steps get automated first: start from the safe end (checks, implement — a mistake there is one revert, caught by gates) and move toward the valuable end (design decisions). The review gates at that end are never automated at all. The team decides when to move a dial, reading the step’s run record as advice.
Epiccore
One feature, described well: the problem, the goal, the scope. The unit Shape works on. Gets a stable ID like EP-checkout.
Story (user story)core
A slice of an epic small enough to build and review on its own. Each story is repo-tagged — it lists which code repos must implement it (e.g. repos: [backend, mobile]). ID: EP-<slug>-S01.
Atomic taskcore
The smallest unit of building: one task = one branch = one commit = one PR, with a small diff (≤3 files) that stays inside the files the task declared. ID: EP-<slug>-S01-T03.
Handoff rulecore
Where files live: everything up to and including the locked contract lives in the Product; everything from the spec onward lives in each code repo. The handover point is exactly where Spec Kit begins.
Code-aware (the brain reads the code)core
When code repos are connected, each Shape author step first loads their cached code-maps — so the epic references what already exists, the architecture cross-checks the contract against real endpoints before locking it, the UI reuses existing components, and stories anchor to real modules.
Workspace (.yad-workspace.json)core
The folder that holds the Product (product/) and the code repos side by side. yad new, yad init and yad join leave a small .yad-workspace.json in it that holds the Product’s path, so a Product command run from inside a registered code repo still finds the Product.
Front doors (yad new / init / join)core
The three ways in. yad new <name> makes a new product (<name>/product/) and runs setup; it creates no remote and prints the gh/glab line for you to run. yad init is for repos you already have. yad join <url> is for a teammate: it clones the Product and every repo it registers, then adds only per-machine files (git-ignored skill copies and the git pre-commit hook) — it never commits or pushes. yad repo clone later fetches any registered repo still missing on your machine.
Foundationcore
The optional Product level, run once per product before any epic. yad foundation new seeds it in foundation/ (id EP-foundation); the yad-discovery skill writes its sections (purpose, scope, MVP, roadmap.md, stack, repos, and optionally market and risks). It has one review and no Build, and ends at foundation-done. yad foundation status reads which roadmap features have started. An older product’s epics/EP-discovery/ is converted by yad migrate.
Lifecycle profilecore
The step chain an epic is seeded with by yad epic new --profile: classic (the 10-step chain, epic first), analysis-first (12 steps, analysis first), chore (epic and stories only, for upkeep) or spike (a chore with analysis in front, for an investigation). The two short lanes have no architecture gate, so they may not move the contract.
Solo / team mode (yad mode)core
Who must approve. Solo waives approvals on every review gate — the merge still decides. Team counts them. yad mode solo --reason <why> and yad mode team switch it and record who, when and why; setup asks it first.
Skip / defer / unblockcore
Ways to set an optional step aside, each with a recorded reason. yad skip <epic> <step> --reason marks it not needed (for example the UI step of a backend-only epic). yad defer … --reason [--debt] sets it aside to do later; its review is still owed, and --debt makes yad next and yad doctor remind you. yad skip <epic> <story> --repo <name> skips a whole Build lane a story does not need. yad unblock clears a recorded blocker. Each has an undo (unskip, undefer).

Files & artifacts

Artifactfiles
The file an author step produces (e.g. epic.md, contract.md). An author step writes its artifact, marks itself done, and stops at its review gate.
analysis.mdfiles
The optional discovery brief: the analyst pressure-tests the raw idea before the epic is written. If skipped, the epic step does this shaping inline.
epic.mdfiles
The agreed description of the feature. Authoring it assigns the epic’s EP-<slug> ID and seeds the epic’s state files.
architecture.mdfiles
How the feature will be built technically: stack, components, data flow.
Contract / contract.mdfiles
The locked shared surface between repos: API shapes, events, and the data model that backend, mobile and dashboard all obey. There is exactly one contract per epic, kept in the Product; code repos quote it, never re-invent it.
Contract surfacefiles
The specific block inside contract.md (between CONTRACT-SURFACE:BEGIN/END markers) that is hashed and locked. Changing anything in it is a “contract change”.
Contract lock / contract-lock.jsonfiles
A SHA-256 hash of the contract surface, recorded when the architecture is authored. If the surface ever differs from its lock, approvals are invalidated and the change must go back to the architecture gate.
ui-design.md + DESIGN.mdfiles
The UI artifacts: the design decisions for this epic plus the reusable design language, authored with the ux-designer (driving Impeccable when installed).
stories/files
One markdown file per story (EP-<slug>-S0N.md), each tagged with the repos that must implement it.
File ledgergates
The set of state files that is the single source of truth for reviews: approvals.json, comments.json, reviews/*.md. Platform PRs feed into the ledger; the ledger always wins.
state.jsonfiles
The epic’s state machine on disk: every step, its two dials, its status, and currentStep (where the epic is right now).
approvals.jsonfiles
Who approved which review, recorded under the approver’s platform login (no role, no domain). The gate reads this to decide whether the rule is met.
repos.jsonfiles
The project-wide registry of connected code repos (path/URL, platform, freshness sha). It stores no people.
schemaVersionfiles
The shape a state file is in, stamped as the first key of every JSON object yad writes under .sdlc/. It lets a later release recognise a file written by an older one and upgrade it instead of guessing. A file without it counts as version 1, so older projects keep working untouched; the list files (approvals.json, comments.json, product-prs.json and its older copy hub-prs.json, reconcile-debt.json) never carry it because a JSON list cannot hold a key. Not the same as cli-version.json, which records the CLI release rather than the file's shape.
product.jsonfiles
The Product’s platform record (GitHub or GitLab), used to run Shape reviews on real PRs/MRs. It stores no people. Also written under its older name, hub.json, until v5.
Roster (removed)roles
An older list of people and roles in the Product settings (product.json). yadflow no longer keeps one: repository access is the list, the platform records who approved, and yad roster only prints a notice that it was removed. A roster in hub.json, domain_owner(s) in repos.json, or a .sdlc/verified-authors file that an older release wrote is left on disk and decides nothing (the roster's name → login pairs are used only to record each person's login on older approvals; yad doctor says when no older record needs them) — yad doctor warns people:roster-unused, people:domain-owners-unused or people:verified-authors-unused so nobody believes it still decides anything.
Code-mapfiles
A lightweight, AI-readable summary of a connected code repo — its existing endpoints, events, data models and modules — cached under .sdlc/code-context/ so the Shape steps don’t contradict code that already exists.
Repomix packtools
A compressed, secret-scanned snapshot of a repo’s code produced by the Repomix tool (npx repomix@1.18.1), cached alongside the code-map so AI can read the codebase.
Fresh / stalefiles
A connected repo’s cached picture is fresh if the repo hasn’t moved since it was packed (tracked by HEAD sha) and stale if it has. Refreshing is a deliberate human decision (yad repo refresh) — skills warn about staleness but never silently re-pack.
code-context: frontmatterfiles
A stamp each Shape artifact carries recording exactly which repo code-maps (and at which sha) it read while being authored.
build-log.jsonfiles
The record of every ship: which task, which PR, which merge commit — keeping the epic → story → task → PR chain traceable both ways. Written shard-then-fold (one shard file per entry, so parallel stories of an epic never conflict); yad tidy up folds a shipped story's shards back into the single folded file.
build-state/<story>.jsonautomation
Per story: the Build steps with their automation dials and statuses, per repo. What yad-run reads to know whether to advance or stop.
ready-for-buildcore
The milestone state an epic reaches when all Shape gates have passed. From here, stories can enter Build.
in-build / shippedbuild
A story’s lifecycle status during and after Build: in-build once its first task merges, shipped when the story is fully delivered.
index.json / yad historyfiles
.sdlc/index.json is the Product’s one-file front door: one summary line per work item, rebuilt from each item’s own files by yad index (on the default branch only; on a verified Product, CI writes it). yad history lists every work item newest first, yad history show <id> shows every step with its closing record and approvals, and yad history search <text> finds items — all built live, writing nothing.

Gates & review

Review gate (yad-review-gate)gates
The one reusable team review loop used by every Shape review: open → comment → approve → advance. Commenting never advances; advance moves forward only when the approval rule is met — otherwise it says exactly what is still missing.
Basegates
The part of the approval count that is always enforced — and, for now, the only part: at least 1 distinct approver who is not the author. Every team review needs it, together with resolved threads and a merged review PR.
Approver countgates
How many distinct people a step asks to approve: base 1 plus its risk step (+2 for contract, +1 for auth/payments). It names no person and no role. Only the base is enforced; the risk step is advisory — reported as a shortfall (“1 short”) against the count capped at the active people less one (never below 1). The gate rule label is count.
Risk stepgates
What a step's risk tags add to the base: +2 for contract, +1 for auth or payments — the largest step, never the sum. So the architecture + contract review asks for 3 approvers. Advisory: enforcing it is parked (roadmap row E108). (This replaces the older “escalated” and “per-repo” rules, which added named reviewers per repo; the stories review is now an ordinary count gate.)
Artifact ownerroles
The person named in an artifact’s owner: frontmatter, who addresses comments. It is not a gate role: approvals come from anyone with access who is not the author.
Reviewerroles
Anyone with access to the repo who reads, challenges and comments on an artifact, and records an approval when satisfied. The approval is recorded under their platform login.
No-platform gategates
The gate run purely on files, when the Product has no GitHub/GitLab: yad gate comment <epic> <artifact> --by <name> records who commented, yad gate approve … --by <name> records an approval bound to the artifact’s content (an edit revokes it), and yad gate advance <epic> <artifact> passes the gate when its approvals hold. With a platform these three commands refuse — the PR/MR carries the review.
Ledger mode (local / verified)gates
Who writes the review files (the ledger), set by ledger in product.json. local — your machine writes them (no platform, or a platform with no gate-sync CI). verified — the default with a platform: CI is the only writer, at merge, and a person’s hand edit is refused by the ledger guard.
PR-driven gategates
When the Product is on a platform: each artifact’s review rides a real PR/MR. Reviewers approve/comment there, and the step advances on merge once the rule is met and every comment thread is resolved. On a local ledger, yad gate sync maps the PR state into the file ledger; on a verified one CI does it at merge (yad gate ci --merged) and yad gate sync is advisory. The merge click is the human approval act.
Product bridge (yad-product-bridge)gates
The machinery that connects the file ledger to platform PRs/MRs: opens the review PR per artifact, labels it (domain:<repo> for touched repos) without requesting reviewers, and provides the read-only gh/glab recipes for syncing approvals and comments back.
Merge-time gate syncgates
A CI workflow on the Product that runs yad gate ci on merge. In verified ledger mode CI is the sole writer of the ledger, and writes only at merge, on the default branch. During review CI writes nothing: the platform PR/MR is the source of truth (native approvals + threads), and CI never touches the review branch — so an in-flight approval is never dismissed and required checks never strand. On the human merge it re-reads approvals, advances the step, and flips the artifact status on the default branch. The sweep that catches a missed merge keeps re-visiting each merged review for a week — that costs a read, not a commit, because the ledgers are written in a canonical order and an unchanged record re-serializes to an identical file (#163). A ledger-guard check keeps humans out of the gate files — with one carve-out: a brand-new epic's seed, which no CI path can write, so it rides the epic's first review PR/MR (creation, not mutation). CI never approves and never merges; the human keeps the merge click, then git pulls.
Ledger guard (three layers)gates
On a verified Product, three things keep hand edits out of the CI-owned review files: a harness hook that refuses an agent’s edit, a git pre-commit hook in each clone (installed by yad check --fix and yad join) that refuses a person’s commit, and the ledger-guard CI job on the PR. The one door past the local hook is yad commit --manual --reason <why>, which records a Ledger-Override trailer — the CI job still judges the commit and quotes the reason. Which branch rules to turn on is in docs/branch-protection.md.
Approval revocation (re-hash)gates
If a reviewed artifact actually changes after approval, the recorded approvals are revoked automatically (the artifact is re-hashed) — reviewers get a fresh pass at the new content.
Risk tags / risk routinggates
Labels (contract, auth, payments) and the PR template’s Impact & Risk block that decide how many must approve. High risk adds 1 and a touched contract surface adds 2 (risk-route.sh prints the count, e.g. ROUTE: 3 approvers = base 1 + contract risk 2, and lists the touched domains as a hint for whom to ask).
Impact & Risk blockgates
A section in the wired PR/MR template where the author declares the risk level and touched surfaces — the input the risk routing reads.

Spec Kit ceremonybuild
The heavy specification pass run once per story per repo by yad-spec: specify → clarify → plan → analyze → checklist → tasks, writing specs/<story-id>/ in the code repo. It quotes the locked contract; it never widens it.
link.mdbuild
The pointer file written into specs/<story-id>/ that links the spec back to its story in the Product — the thread that keeps the two repos connected.
Spec-link checkbuild
CI gate #1: every code change must link to a real story/spec via the Task: trailer in its commit. No orphan changes.
Contract-checkbuild
CI gate #2: a diff that changes the contract surface without declaring Contract-Change: yes and an updated, re-locked contract fails — routing the change back up to the architecture gate. This is how the contract stays honest.
Build/test/lint gatebuild
CI gate #3: the ordinary safety net — the project must build, its tests must pass, lint must be clean.
Verified-commits gatebuild
CI gate #4: every commit must carry a platform-verified signature — rejecting unsigned commits, on the Product and every repo. There is no author allowlist: write access to the repository decides who may author.
Commit-message gatebuild
CI gate #5: every commit subject must follow Conventional Commits (<type>: …, no trailing period) and its trailers must be ordered Task → Contract-Change → Co-Authored-By. Profile-aware (code|product; hub is the old name for product).
PR-title gatebuild
CI gate #6: the PR/MR title must follow the convention — a Conventional-Commits subject on code repos. On the Product it splits by head branch: a review/EP-* branch is a Shape review PR and needs a review: <artifact> (EP-<slug>) title, while any other branch is a Product tooling/code change and uses the Conventional-Commits subject. Anti-bypass: a non-review branch that changes a Shape artifact (epics/**) is rejected — artifact edits must go through a review PR.
PR-template gatebuild
CI gate #7: the PR/MR body must actually use the committed template (its required sections present + the risk field filled), so the review and routing have their inputs. Profile-aware (code|product; hub is the old name for product); the Product splits by head branch the same way as the PR-title gate, with the same epics/**-on-a-non-review-branch anti-bypass guard.
Task: trailerbuild
A line at the end of every commit message naming the story + task it implements (e.g. Task: EP-checkout-S01-T03). What the spec-link check verifies.
Contract-Change: yes trailerbuild
A commit trailer added only when the diff deliberately touches the locked contract surface — paired with an updated, re-locked contract, or the contract-check fails.
Conventional Commitsbuild
The commit/PR title convention used everywhere: feat: …, fix: … (lowercase after the type). feat:/fix: commits also set the CLI's own next version number — though merging one never publishes on its own: a person releases by fast-forwarding the release branch.
Co-Authored-By AI trailerbuild
An optional per-commit trailer crediting the AI tool that helped (claude / copilot / cursor / coderabbit). The human author always owns the commit.
Scope guard / scope overrunbuild
The implement step’s hard boundary: the diff must stay inside the files the task declared. If it would grow beyond them, the step flags it and STOPS — and during automated runs this always halts for a human, overriding any dial.
AI review (advisory)build
An automated first-pass review of the PR (e.g. CodeRabbit). A second set of eyes, never the authority — the human engineer review still owns the merge.
Engineer reviewbuild
The final human gate: an engineer reads the diff against the spec and owns the merge. The same count rule: 1 approver who is not the author, with high risk or a contract surface raising the advisory count. Permanently human — never automated.
Backfill (yad-backfill)build
For existing/legacy code: pack one feature with Repomix, have AI draft a spec of what exists (“describe, don’t invent”), mark it DRAFT/unverified, and require human approval before it counts. New work on that feature is blocked until its spec is approved — gated per touched feature, never the whole repo.
Draft / unverified specbuild
A backfilled spec before a human has approved it. It describes existing behaviour but doesn’t yet count as real for gating purposes.
Do-not-touch zonesbuild
Parts of an existing codebase marked off-limits to AI changes — part of the setup when adopting the workflow on a brownfield project.
Risk map (.sdlc/risk-map)build
A file in a code repo that gives a risk level per folder (no names). The risk-map CI job reads it to report the approver count and warns when it has gone stale; yad risk-map check and yad risk-map draft look after it. Advisory — it never blocks a merge.

Drafting together (Shape authoring)

Capture (yad capture)core
Saves every changed Shape artifact onto your own private branch, yad/wip/<git-name>/<epic>, and pushes it — never touching your checkout. A harness hook runs it after each agent edit, so drafts are never lost.
Claims (yad claims)core
Shows who else is editing which artifact, read from everyone’s capture branches. Advice, not a lock: a claim ends 4 hours after the last save, or once the file is merged.
Fold (yad fold <epic> <step>)core
Ends an authoring step: commits that step’s artifacts as one clean commit (docs(<epic>): author <step>). The drafts stay on the yad/wip/… branch. On a local ledger the epic’s ledger rides along in the same commit.
Step owner (yad assign / unassign / owners)roles
Names one person (by git name) as the owner of an authoring step, in .sdlc/owners/<step>.json. Advice, not a lock: the capture hook warns anyone else who edits that step’s files. yad owners lists every assignment.

Automation & trust

Orchestrator (yad-run)automation
The engine that drives a story’s Build (spec → tasks → implement → checks) reading each step’s automation dial: on advance: auto it advances alone; on advance: human it stops; on any failure, scope overrun, or contract-surface touch it halts and pulls in a human. It always stops at the engineer review.
Setting the dial (yad dial)automation
The team switches a step to advance: auto itself. yad dial shows the step’s run record beside the dial as advice and never refuses on it — nothing has to be earned (E34). A review gate is always refused. A Shape author step’s dial is recorded for the whole project, and nothing acts on it yet.
Trust log (trust-log.json)automation
The evidence base: every orchestrated run’s verdict is recorded here. It is the run record yad dial shows the team as advice. Written shard-then-fold (one shard file per entry, so parallel writers never conflict); yad tidy up folds a shipped story's shards back into the single folded file.
Checkpoint (yad checkpoint)automation
Commits the machine-written Build ledgers — trust-log.json, build-log.json, build-state/<story>.json — plus any story status: flip (→ in-build/shipped) now backed by a build-log ship (#112) — as one chore(product) audit-trail commit so no human hand-commits them. The Build analogue of the Shape yad gate ci sync: it stages only those ledgers + ship-backed story flips by an explicit allowlist (never a Shape gate file, so ledger-guard never trips) and commits only on the default branch. Carrying the story flip keeps the artifact from drifting from build-log.json, so no operator falls back to a raw git-to-main push. Called by yad-run each loop iteration and by yad-engineer-review after recording the ship.
Tidy up (yad tidy up)automation
Folds a shipped story's finished trust-log/build-log shards back into the single folded ledger file, as one chore(product) commit — the manual "pack it up" companion to the shard-then-fold storage, and the analogue of loose git objects → git gc. Concurrent Build writers each write their own shard file so parallel stories never conflict; readers union the folded file + loose shards, and tidy up is the on-demand compaction. Default branch only, --push to push; a no-op when nothing is foldable.
Run recordautomation
What yad dial prints beside a step’s dial: how many times it ran in that repo and how many of those were “approved-unchanged”. Advice, never a rule — the trust threshold was removed in E34.
Run verdictsautomation
How each engineer review scores an automated run: approved-unchanged (merged exactly as authored — the strongest signal), approved-with-edits (a human fixed it first), rejected (failed).
Kill switchautomation
yad kill --reason "<why>" — one move that holds every step at advance: human instantly, recorded with who, when and why in .sdlc/automation.json. yad unkill turns it off. Automation is always reversible in one move.
Locked stepsautomation
The steps that may never be set to advance: auto: every review gate — each Shape review and the engineer review. A gate advances only on a human act.
Fleet roll-upautomation
The cross-epic summary yad-status prints: where every epic stands and which Build steps wait at a human gate, at a glance.

5. Project types — greenfield, brownfield, and multi-repo

The same workflow runs for every project type — only the one-time setup differs. The design doc defines three project types; multi-repo is an orthogonal option that works with any of them.

Type 1 — Greenfield (new project, full AI)

What it means: a brand-new project with no existing code. Specs are written from the very start, so there is never undocumented behaviour to protect.

Setup differences: the lightest path — no backfill, and you simply skip yad-connect-repos until code exists (the brain proceeds without code-maps; the steps are explicitly “greenfield-safe”). For UI, run Impeccable’s craft first to create the design, then extract to seed the design language.

Setupyad new <name> (makes the Product repo + runs setup, installing the skills) · create empty code repos · wire each repo (CI gates + PR template) · connect-repos skipped — nothing to map yet
▼
Shape(analysis) → epic → architecture + contract → UI (craft → extract) → stories — all human-gated; then test cases runs in parallel with Build
▼
Buildspec → implement → checks → PR → ship, per story per repo — specs exist for 100% of the code from day one
▼
Later: connect the repos once they have real code, so future epics become code-aware

Type 2 — Brownfield, already using AI

What it means: an existing codebase where the team already works with AI tools. The code is real and live; the risk is new work silently breaking what exists.

Setup differences: connect every repo (yad-connect-repos) so the brain reads what is already built; add the spec-link check so every change links to a story; and mark the “do-not-touch” zones AI must not modify. Run yad-backfill before a new feature touches an old one. For UI, run Impeccable’s document first (read the current UI), then extract, then craft new designs that match.

▼
Shape — code-awareeach author step loads the code-maps: the epic references existing behaviour, the architecture cross-checks the contract against real endpoints before locking it, UI reuses existing components (document → extract → craft), stories anchor to real modules
▼
Touching an old, unspecced feature?run yad-backfill first: Repomix-pack that one feature → AI drafts a “describe what exists” spec → DRAFT until a human approves → only then may changes touch it
▼
Buildsame as always — spec → implement → checks (incl. contract-check) → PR → ship

Type 3 — Brownfield, no AI yet

What it means: an existing codebase and a team adopting AI for the first time. Trust must be built before AI touches anything important.

Setup differences: same wiring as Type 2, but start AI on safe tasks only — tests, docs, refactors — with every dial at advance: human. Run the backfill step before any new feature touches old code. Switch automation on slowly: read each step’s run record (from the trust log) and move one dial at a time with yad dial, exactly as the end-first rule prescribes.

Setupyad init · wire + connect repos · everything at advance: human · AI assistance limited to safe tasks (tests, docs, refactors)
▼
Backfill firstbefore new features touch old code, produce human-verified specs for the features they touch
▼
Shape + Build, fully manual gatesthe team learns the rhythm: author → gate → approve, with heavy AI assistance but zero AI advancement
▼
Switch automation on step by stepread each step’s run record, then yad dial checks to auto first, then implement — end-first
▼
Kill switch always availableyad kill --reason — back to fully manual in one move

Option for all types — Multi-repo stories

A story tagged repos: [backend, mobile] simply runs Build in each repo independently — but every repo builds from the same one locked contract in the Product. The contract-check blocks a surface bypass in either repo, so the repos can never drift apart.

When Whenever a member wants to understand what is being built — to review a gate with confidence, onboard onto a domain, or grow a skill. It is additive and reversible: learning never gates the work.

Shape — author the thinking (in the Product)

yad-discovery (optional · the Foundation)

What Writes the Foundation — the Product level, run once per product before any epic. With the analyst and pm lenses it frames the product and writes one file per section into foundation/: purpose, scope (what it is and is not), MVP, roadmap.md (the feature menu each yad-epic reads), stack, repos, and optionally market and risks. Greenfield and brownfield (brownfield reads the connected code). Its id is EP-foundation; its one review ends at foundation-done (there is no Build). That approval is reported, not enforced: yad next says when epics go ahead of it. The skill keeps its old name; an older product’s epics/EP-discovery/ is converted by yad migrate.
How In the Product, seed it, then describe the product:
yad foundation new
run yad-discovery — idea: "an online shop where customers place and track orders"
yad foundation status      # which roadmap features have started (read-only)
When At project kick-off, to frame the whole product before the first epic. Skip it freely — a team that already knows what to build can start at yad-epic.

yad-analysis (optional)

What A dedicated discovery pass: the analyst AI pressure-tests your raw idea — is it worth building, for whom, what could kill it — and writes the brief into analysis.md. It assigns the epic’s EP-<slug> ID and seeds the state files.
How In the Product, just describe the idea:
run yad-analysis — idea: "let customers check out a cart and track their orders"
When Before the epic, when the idea is still fuzzy and deserves its own gated discovery round. Skip it freely — the epic step does the same shaping inline.

yad-epic

What Writes the feature down properly: problem, goal, scope, the repos it will touch → epic.md. The analyst shapes the idea, the pm writes the epic. If analysis didn’t run, this is the entry point: it assigns the EP-<slug> ID and seeds .sdlc/ state. If repos are connected, it reads their code-maps so the epic references what already exists.
How In the Product:
run yad-epic — feature: "cart checkout and order tracking"
When The start of every new feature (or right after the analysis gate passes). It ends by stopping at the epic review gate.

yad-architecture

What With the architect AI, decides how the feature is built (architecture.md) and writes the locked contract (contract.md) — the one shared surface (APIs, events, data model) every repo must obey. It hash-locks the contract surface into contract-lock.json. Code-aware: it cross-checks the surface against existing endpoints before locking.
How In the Product, after the epic gate passes:
run yad-architecture — epic: EP-checkout
When Right after the epic review is approved. Stops at the architecture review gate, which carries the contract risk tag (count 3 = base 1 + contract risk 2; the base is enforced).

yad-ui

What With the ux-designer AI, authors the UI design for the epic: ui-design.md (this feature’s screens and flows) + DESIGN.md (the reusable design language). Drives Impeccable’s document / extract / craft commands when installed; writes the files directly when not (and records that). When a design tool is connected (yad-connect-design), it also materializes the screens in that tool — generating them from the spec or linking an existing design — and records the screen→frame map in design-links.json; otherwise it stays markdown-only.
How In the Product, after the architecture gate passes:
run yad-ui — epic: EP-checkout
When After architecture, before stories. Skip-able only if the epic genuinely has no UI. Stops at the UI review gate (base count).

yad-stories

What With the pm AI, slices the approved epic into user stories small enough to build — one file each under stories/, with stable IDs (EP-<slug>-S01…) and a repos: tag naming which code repos must implement each one. Reads epic + architecture + contract + UI as input.
How In the Product, after the UI gate passes:
run yad-stories — epic: EP-checkout
When After the UI gate passes. Stops at the stories review gate (an ordinary count gate). When it passes the epic is ready-for-build — Build can start, and yad-test-cases opens in parallel.

yad-test-cases

What With the test architect AI, authors the risk-based test cases that cover the approved stories → test-cases.md (cases prioritised P0–P3, with story→case traceability). When a testing tool is connected (yad-connect-testing), it also implements the automation tests in that tool — generating them into the connected code repo(s) or linking an existing suite — and records the case→test map in test-links.json; otherwise it stays artifacts-only. Reads epic + architecture + contract + UI + stories as input.
How In the Product, after the stories gate passes:
run yad-test-cases — epic: EP-checkout
When A parallel, non-blocking track: it opens the moment the stories gate passes — the epic is already ready-for-build, so this runs alongside Build, not before it. Stops at its own test-cases review gate (base count); that review never blocks building.

The review gate & its plumbing (cross-cutting)

yad-review-gate

What The one reusable team review loop used by every Shape review. It shows the artifact, records comments and approvals as files, enforces the approval count (1 approver who is not the author; contract/auth/payments raise the full count, which is advisory), and moves the step forward only when the rule is met.
How In the Product, one action at a time:
yad-review-gate epic: EP-checkout artifact: epic.md action: open      # present it for review
yad-review-gate … action: comment    # record a reviewer's notes (never advances)
yad-review-gate … action: approve    # record an approval (platform login)
yad-review-gate … action: sync       # pull approvals/comments from the Product review PR
yad-review-gate … action: advance    # move on — only if the rule is met, else it says what is missing

# with no platform, comment / approve / advance are these commands:
yad gate comment EP-checkout epic.md --by sara
yad gate approve EP-checkout epic.md --by omar
yad gate advance EP-checkout epic.md
When After every author step — the artifact is written and waiting. With no platform use open → comment → approve → advance. With a platform, reviewers work on the review PR/MR and the merge advances the step: on a local ledger add sync; on a verified ledger CI records it all at merge, and the skill writes nothing to the ledger itself.

yad-product-bridge

What The bridge between the file ledger and real PRs/MRs on the Product: opens a review PR per artifact and labels it (it requests no reviewers), and provides the read-only gh/glab recipes that pull platform approvals and comments back into the files. The file ledger always stays the source of truth.
How Mostly invoked for you by the gate (its open/sync). You call it directly once, to wire the event-driven sync CI:
yad-product-bridge action: wire    # Product CI runs `yad gate ci` when a review PR/MR merges (+ a 15-minute catch-up sweep)
When Once during setup (step “wire the Product”), if you want Shape reviews to ride real PRs/MRs. No platform or no gh/glab? Everything degrades to the local gate with no error — you never need this skill.

yad-review-companion

What Makes reviewing easier on any review PR/MR — a Shape artifact review (yad gate) or a Build code PR (yad review). It writes a 60-second trailer of what changed and where the risk is, deals small review cards, and runs a chat that answers only from the real material. It marks an approval that came through it as engagement: verified, and posts a friendly nudge on a bare approval. It never blocks anything.
How Ask for it on the PR you are reviewing:
run yad-review-companion — epic: EP-checkout artifact: architecture.md   # a Shape review
run yad-review-companion — repo: backend pr: 42                          # a Build code PR
When Whenever you are about to review and want the short version first. If the Product sets requireEngagement, only approvals marked verified count.

yad-pair-review

What A guided, two-way review session. The AI walks you through the change one stop at a time, highest risk first, explains each stop and asks you a question; you answer and ask back, until you are both satisfied. It also teaches a review method, scores the session against it, and records your progress in the local-only learning ledger. Genuine concerns become normal blocking comments; the session itself never blocks a merge or a gate.
How
yad-pair-review repo: backend pr: 42 action: walkthrough          # a Build code PR
yad-pair-review epic: EP-checkout artifact: epic.md               # a Shape review (walkthrough is the default)
yad-pair-review … action: rubric                                   # just print the review method
When For a risky change you want to understand properly, or to learn how to review. It is a skill, not a yad command; its CLI side is yad gate walkthrough (Shape) and yad review walkthrough (code PRs), which print the ordered stops.

Build — turn stories into shipped code (in a code repo)

yad-spec — Build Step A

What Runs the heavy Spec Kit ceremony once for one story in one repo — specify → clarify → plan → analyze → checklist → tasks — writing specs/<story-id>/ inside the code repo plus a link.md back to the story. It quotes the locked contract; it never widens it. Drives /speckit.* when installed, authors the same files by hand when not.
How From the code repo (or naming it):
yad-spec story: EP-checkout-S01 repo: backend
When The first build step for every ready-for-build story — once per repo the story is tagged with. The tasks it produces feed yad-implement.

yad-implement — Build Step B

What With the dev AI, implements one atomic task from the story’s tasks.md as a small diff (≤3 files) on its own branch: one task = one branch = one commit = one PR. The diff must stay inside the files the task declared — if it would grow, the skill flags it and STOPS. The commit follows the convention (Conventional subject, Task: trailer, optional AI co-author, Contract-Change: yes only if the locked surface is touched).
How Once per task, repeating until the story’s tasks are done:
yad-implement story: EP-checkout-S01 repo: backend task: T01
# then commit + open the PR with the CLI:
yad commit --type feat -m "create order endpoint" --ai claude
yad open-pr --repo backend
When After the story is spec’d. Run it once per task ID (T01, T02, …). It hands off to the check gates — never merges anything itself.

yad-checks — Build Step C

What The production-safety CI gates: spec-link (every non-maintenance commit links a real story/spec, checked per commit; ci/chore/build/test commits are exempt), contract-check (a contract-surface diff without a re-locked contract FAILS), build/test/lint, verified-commits (every commit platform-signed; no author allowlist), and the pattern gates — commit-message (Conventional subject + trailer order), pr-title, and pr-template (the PR/MR body uses the template). A code repo gets 11 jobs: those seven plus risk-map (advisory — reports the approver count from .sdlc/risk-map) and the three feature-thread gates lineage-check, epic-open and reconcile-debt. The pattern gates are profile-aware (code|product), so they run on code repos and the Product, where they sit beside the ledger-guard job. wire installs them into the repo’s CI (merging with any existing CI, never clobbering); run executes them right now, locally.
How
yad-checks repo: backend action: wire   # once, during setup
yad-checks repo: backend action: run    # before opening each PR
yad-checks repo: product action: wire       # Product-flavored gates
When wire once per repo at setup; run after implementing, before the PR — the same gates also run automatically in CI on every PR and must pass before merge.

yad-pr-template — Build Step D

What Detects the repo’s platform and commits the matching PR/MR template, which carries an Impact & Risk block. A high risk level adds 1 to the approval count and a touched contract surface adds 2 — an auth or payments surface adds nothing unless the risk level is high. route reads a PR body and prints the count and the touched domains, as a hint for whom to ask. It also ships the pr-title.sh / pr-template.sh gate scripts that yad-checks runs.
How
yad-pr-template repo: backend action: wire    # once, during setup
yad-pr-template repo: backend action: route   # how many must approve, and which domains to ask?
yad-pr-template repo: product action: wire        # the Product's Shape review template
When wire once per repo (and the Product) at setup; route whenever you’ve opened a PR and want to know how many must approve and which domains to ask.

yad-commit — Build helper

What Commits one staged atomic change by the conventions: a Conventional-Commits subject, the fixed trailer block (Task → Contract-Change → Co-Authored-By), and a ≤3-file atomic guard. The human git author owns the commit; an assisting AI is recorded only as a Co-Authored-By footer chosen per-commit with --ai (default none, human-only).
How From the repo holding the staged change:
yad commit --type feat -m "add the order endpoint" --ai claude
yad commit --type fix -m "handle null user" --dry-run   # preview only
When Any time you have a staged atomic change to commit by the rules — on a code repo or the Product.

yad-open-pr — Build helper

What Opens a code-repo task PR/MR from the committed platform template: detects GitHub/GitLab, pushes the task branch, and creates the PR/MR with the body prefilled and the title defaulting to the commit subject. It requests no reviewers — the command prints no reviewers were requested — ask them on the PR itself. It never merges.
Base Targets the repo’s resolved default branch — registry default_branch, else the platform’s own default, else origin/HEAD, else main — never a hardcoded main. It warns when the base is not the platform default, because CodeRabbit skips auto-review on a non-default base and retargeting afterwards does not undo it.
How On the task branch:
yad open-pr --repo backend --risk low
When After committing a task, to raise its PR/MR for the check gates + engineer review.

yad-ship — Build helper

What Does both routine Build hand-actions for one task in one step: commit by convention, then open the task PR/MR. A thin wrapper over yad-commit then yad-open-pr — the PR step runs only if the commit lands (a failed commit, tripped guard, or --dry-run stops before pushing). It never merges.
How On the task branch, with the change staged:
yad ship --type feat -m "add the order endpoint" --ai claude --repo backend --risk low
When The common case — turn an implemented, staged task into a reviewable PR/MR in one command.

yad-engineer-review — Build Step E

What The last mile of a task’s PR: ai-review triggers the advisory AI pass (CodeRabbit — a second set of eyes, never the authority); approve records the human engineer approval (the same count, reported only: branch protection holds the merge, risk step advisory); ship merges and records the ship in build-log.json, moving the story to in-build → shipped so the epic → story → task → PR chain stays traceable.
How Against the task’s PR, in order:
yad-engineer-review story: EP-checkout-S01 task: T01 repo: backend action: ai-review
yad-engineer-review … action: approve     # the human engineer's approval
yad-engineer-review … action: ship        # merge + record in build-log.json
When Once a task’s PR is open and the check gates are green. The engineer approval here is permanently human — no dial can ever automate it.

yad-backfill — Build Step G

What Writes specs for code that was built before the workflow existed, so new work doesn’t break it. It packs one feature at a time with Repomix (secret-scanned), has AI draft a “describe what exists, do not invent” spec marked DRAFT/unverified, and requires a human approval (through the same review gate) before the spec counts. Until then, changes to that feature are blocked — gated per touched feature, never the whole repo.
How
yad-backfill repo: backend feature: health   # globs e.g. src/health/**
When Brownfield projects, before a new story touches an old, unspecced feature. Never needed on greenfield.

Automation & status

yad-run

What The orchestrator that makes automation real. It walks a story’s Build (spec → tasks → implement → checks) reading each step’s automation dial: advance: auto → it proceeds alone; advance: human → it stops for you. Any failure, scope overrun, or contract-surface touch halts and pulls in a human, and it always stops at the engineer review. Every run lands in the trust log. Its dials are set with yad dial, and the kill switch is yad kill / yad unkill.
How
yad-run story: EP-checkout-S02 repo: backend        # drive Build on the dials
yad dial EP-checkout EP-checkout-S02 --repo backend checks --to auto    # shows the run record as advice
yad dial EP-checkout EP-checkout-S02 --repo backend checks --to human   # revert — always allowed
yad kill --reason "bad deploy"   # everything back to human, recorded, instantly
yad unkill                       # each step follows its own dial again
When Entirely optional — ignore it at first; every step is human-approved by default. Reach for it when the team wants a Build step to run on its own — read the step’s run record first. Use yad kill the moment anything feels wrong.

yad-status

What A read-only dashboard in text: the epic’s full step chain, every step’s two dials and status, the contract lock, which approvals the active gate is still waiting on, each Build step’s run record (advice only), the kill-switch state — and across epics, the fleet roll-up. It changes nothing.
How
run yad-status                    # everything, across epics (fleet view)
run yad-status — epic: EP-checkout   # one epic in detail
yad next                          # the CLI's own answer: the one next action to take
When Any time, freely — it’s the “where are we and what’s blocking?” skill (there is no yad status command; yad next and yad history show are the CLI views). The best first move whenever you’re unsure what to do next.

yad-report

What The self issue reporter. When a yad flow breaks, it files a well-formed bug in the upstream yadflow repo so maintainers can fix it — with auto-scrubbed diagnostics. The payload is allowlist-only: the yadflow/node/os version, tool present+authenticated booleans, the Product platform enum, the error code/hint, a path-scrubbed message, and the failing command + flag names. It never posts absolute paths, hostnames, git URLs, repo names, logins/emails, epic/story IDs, branch names, or flag values. It searches open issues first (dedupe), shows you the exact payload and asks before posting, then files via an authenticated gh/glab or a prefilled issues/new URL. Reuses your local gh/glab session — no stored tokens. Never a gate; never touches epic state.
How
yad report                          # file a bug (asks for a one-line summary)
yad report -m "gate sync hangs"     # with a summary
# also OFFERED automatically after an unexpected failure (interactive only)
YAD_NO_REPORT=1 yad …               # opt out of the auto-offer
When Whenever a flow errors out and you want the maintainers to see it — or just accept the “Report this failure?” prompt after a crash. Disabled automatically in CI (SDLC_NONINTERACTIVE).

yad-change Phase 6

What The post-lock change/defect/hotfix intake. After a feature's contract locks and its stories ship, you don't edit the locked artifacts — a change becomes a new epic threaded to its parent. yad-change triages the depth (defect-fix / behavioral-no-surface / contract-surface / new-capability), writes the new EP-<slug>'s lineage frontmatter and change.json (recording a defect's escape_stage + root_cause), then seeds its ledger with yad epic new --parent — an inherited-step state.json and a pointer-lock contract-lock.json; a hotfix also opens reconcile-debt.json. It inherits the unchanged Shape artifacts by reference and re-authors only what changes — so artifacts are never stale, only superseded. Never auto-advances.
When Whenever a shipped feature needs a fix — or when CI fails with epic-open: targets SEALED epic.

yad-timeline enrichment

What Renders a feature thread (genesis → changes → defects) as an evolution view (the yad-docs shell + TIMELINE.md) and resolves the inheritance chain into thread-resolved.md — the composed current-truth map (which epic owns each artifact now) that AI/humans read to plan the next change. Output enrichment, never a gate.
When To see how a feature evolved, or to get its authoritative current artifacts before the next change.

yad-defects enrichment

What A per-epic/per-thread quality-gap report (the yad-docs shell + DEFECTS.md) that aggregates defects by escape_stage (the gate that should have caught it) and root_cause, so the team sees where the SDLC leaks — e.g. "100% of this feature's defects escaped at the test-cases gate" — and hardens that stage, not just the symptom.
When Retro / quality review — "which gate do our defects keep escaping at?"

yad-reconcile maintenance

What A read-only drift/orphan/debt sweep across feature threads (mirrors yad-docs-sync): shipped code or a repo HEAD advance with no owning change-epic, broken lineage, or open hotfix debt — reported with why. refresh points you at yad-change; wire commits advisory CI. Never a gate — the hard block is the lineage-check / epic-open / reconcile-debt CI gates.
When Periodically, or in CI — to catch a change that shipped without being threaded, or debt left unpaid.

yad-stub Phase 6

What In a brownfield repo, not every built feature has an epic, and yad-change needs a real parent. This makes the smallest real anchor: a tiny epic.md marked as a stub, a seeded state.json and empty ledgers. It records only that the feature exists — it never invents behaviour. A defect can thread off it immediately, and yad-backfill later fills it in and promotes it to a real feature epic.
How
run yad-stub — feature: "order refunds" repos: backend description: "refunds a paid order"
When You need to file a bug or change on a legacy feature and there is no epic for it — or yad-change / yad-reconcile point you here.

7. The CLI commands — what each does, how to use it, and when

The yad CLI is the deterministic half of the system — the skills think, the CLI does the predictable file-and-platform work. It’s published to npm as yadflow. For the first run, npx yadflow … needs no install; after that, install it with npm install -g yadflow and run yad. Run it from the Product — or from any code repo the Product registers: .yad-workspace.json lets it find the Product, and it says so on stderr. This section covers the main commands; yad --help and docs/CLI.md list every one.

Start a workspace (the front doors)

yad new <name>  /  yad init  /  yad join <url>  /  yad repo clone

What The three ways into a workspace — the folder holding product/ and the code repos side by side. new makes <name>/product/, runs git init and the setup wizard inside it; it creates no remote and prints the gh/glab line to run yourself. init is for repos you already have: run it in the folder holding them; it makes product/ (or uses the one there), runs setup, and offers each repo it finds. join clones the Product and every repo it registers (a failed repo clone is reported, never fatal), then does only per-machine steps: git-ignored skill copies and the git pre-commit hook. It never commits, pushes, or changes a shared file. All three leave a .yad-workspace.json. yad repo clone is join’s clone step on its own: it fetches any registered repo missing on this machine.
How
npx yadflow new acme       # a new product
npx yadflow init           # repos you already have (run in the folder holding them)
npx yadflow join <url>     # a teammate joining the team
yad repo clone             # later: fetch a newly registered repo
When Once per person: the team lead runs new or init; everyone else runs join.

Install & keep in sync

npx yadflow setup

What The guided first-run wizard (yad new and yad init run it for you). It starts with a profile interview — solo or team (and how many), greenfield or brownfield, monorepo or separate repos, and whether to set up the optional tools now — then: preflight (git/node check), install all 38 skills into the agent dirs you pick, detect the Product’s platform and record the ledger mode (verified with a platform, local without; no reviewers, roles or commit emails are collected), connect a design, testing and learning tool (or defer all three), connect your code repos, wire each one and the Product (CI gates, PR template, gate sync), and optionally write the AI-review config.
How
cd <product-repo>
npx yadflow setup
npx yadflow setup --team 4 --brownfield --separate   # flags pre-answer the interview
When Once per project, by the team lead, from inside the (possibly empty) Product repo — or through yad new / yad init. Teammates run yad join instead. It never re-asks for answers you already gave.

… check  /  … check --fix  /  … update

What The health check and repair tools. check is read-only: it reports what is missing (never installed), drifted (the workflow shipped a newer version), modified (a managed file you edited — yad can prove it from the sha it recorded), stale (a repo’s cached code picture is behind its code), or legacy (an old name or file to replace). check --fix reconciles all of it — filling gaps and applying updates while touching nothing that is already correct, and leaving a modified file alone unless you pass --overwrite-local. update applies drift only (an alias for check --fix --scope=changed); --push also commits and pushes each repo’s changes to its default branch.
How
yad check        # just tell me — read-only
yad check --fix  # and fix it
yad update       # apply updates only
yad update --push   # … and commit + push them in the Product and every repo
When After any workflow update (a new version on npm), or whenever something seems off. Safe to run any time — check changes nothing.

… migrate  /  … migrate --apply

What Moves this project’s state files onto the shape this release expects. Every JSON object yad writes carries a schemaVersion; when a release changes what those files look like, this is the one command that walks an existing project forward. It previews by default — printing a table of what would change and writing nothing — and --apply copies each file it rewrites to <file>.yad-orig before touching it. Safe to run twice: the second run says there is nothing to do. A file newer than your CLI, or one that does not parse, is reported and left alone. When .sdlc/product.json and its older copy .sdlc/hub.json disagree, --apply asks which to keep, and --keep product|hub answers it.
How The full upgrade, run in the Product:
npm install -g yadflow   # 1. install the latest release
yad migrate              # 2. show me what would change (writes nothing)
yad migrate --apply      # 3. do it, backing up first
yad update               # 4. re-sync skills, gate scripts and CI files
yad doctor               # 5. confirm everything is healthy
When After upgrading to a release whose notes mention a file-shape change. Never automatic — an upgrade only happens when you ask for it. Coming from 3.x? Read docs/migrations/upgrading-to-4.md first.

yad doctor

What The environment and state health check: tools and their login, config files, repo paths, every epic’s ledger, and what the platform’s branch protection requires. It exits 1 on any failure, so CI can use it. Read-only.
How yad doctor  ·  yad doctor --json
When After an upgrade, after yad join, or whenever something seems off.

yad detect

What Lists the skills, agents, MCP servers and plugins installed for the AI agents that work here — in this folder and in your home folder — and which agents read each place (Claude Code, Codex CLI, Cursor, Gemini CLI and others). Read-only: it writes nothing, runs nothing and uses no network. An MCP server is named, never its settings, which can hold a token.
How yad detect  ·  yad detect --json (every item, with its version and content hash)
When To see what an agent can use before you bind a skill to a step, or when a skill seems to be missing.

yad toolbox list / check / add / remove

What The entry point the Product’s CI calls. On a verified ledger CI is the sole writer of the ledger, and writes only at merge, on the default branch. Pre-merge it is read-only (nothing is pushed — the platform PR/MR holds the review state). On --merged CI re-reads approvals fresh from the platform, advances the step + flips the artifact status: to approved on the default branch. The wired jobs always name a branch — they discover merged reviews through the platform API and call --branch … --pr … --merged per review. With no --branch it falls back to a local sweep of the review PRs already recorded in the ledger whose step is not yet done (no platform discovery of its own). CI never approves and never merges — the merge click stays human. Idempotent down to the bytes: the ledgers are written in a canonical order, so re-syncing an already-done step — what the 15-minute sweep does for a week after every merge — produces a byte-identical file and commits nothing (before the #163 fix the re-sync re-appended each step’s approvals at the tail, so a sweep rotated approvals.json and committed the reorder on every pass: an unbounded commit loop, issue #163). 8. Competitor analysis — who else does this, and how close they get

Yadflow sits in the spec-driven / AI-governed development market. The honest headline first: as of mid-2026, no single tool on the market offers the exact same package — a team-gated, file-driven SDLC with a hash-locked multi-repo contract and per-step automation the team switches on itself, with a one-move kill switch. But many tools cover slices of it, several with far bigger communities, and one (AWS AI-DLC) shares almost the same philosophy. This section maps them honestly. The competitors, one by one

BMAD-METHOD the nearest “sibling” — and where Yadflow started

What An open-source (MIT) framework of 12+ AI agent personas (analyst, pm, architect, dev…) orchestrated across the full lifecycle. One of the most popular frameworks in the space (~46,700+ GitHub stars, v6.8.0 stable at the time of research). Free. Yadflow was first packaged as a BMAD module; since 4.0 (roadmap row E3) it no longer depends on BMAD, and a team may still bind a BMAD skill to a step with yad skill bind.
Overlap The same Shape order — agents authoring epics, architecture, stories in turn. Anyone could adopt raw BMAD and get a similar solo authoring experience.
Gaps vs this BMAD is fundamentally a solo tool: one person drives it, gates are AI-checked quality gates, not named-human approvals. It has no multi-repo contract, no approval ledger, no PR/MR review bridge, no run record, no kill switch. That delta — a team tool for the same lifecycle — is precisely what this repo exists to add.

AWS AI-DLC (aidlc-workflows) closest in philosophy

What Amazon’s open-source methodology for AI-driven development: adaptive workflow “steering rules” for coding agents. Epics become Units of Work, sprints become Bolts (hours/days), and every phase transition needs explicit human approval — 10–26 verification points per bolt, with team rituals (“Mob Elaboration”, “Mob Construction”) where the team validates AI proposals in real time.
Overlap The deepest philosophical overlap on the market: AI does the heavy lifting, humans hold every gate, AI may never advance on its own. If you pitch Yadflow to an AWS-native team, AI-DLC is the comparison they’ll raise.
Gaps vs this AI-DLC’s gates are rituals, not records — synchronous meetings rather than a durable file ledger with named approvals and an approval count that rises with risk. It has no per-step automation dial (everything stays manual), no multi-repo locked contract, no CI enforcement of spec-links, and no brownfield backfill mechanism. It tells you how to behave; Yadflow gives you machinery that enforces it.

GitHub Spec Kit most adopted — and a component here

What GitHub’s spec-driven toolkit (≈93,000+ stars, v0.8.7, 30+ supported agents): specify → clarify → plan → tasks → analyze → checklist → implement slash-commands plus a project “constitution”. Free, open source.
Overlap Total — by design: Yadflow drives Spec Kit as its Build Step A rather than competing with it. The spec ceremony is literally the same commands.
Gaps vs this Spec Kit covers one pillar only: it specs a feature in one repo for one developer. No team approvals, no cross-repo contract, no review routing, no automation policy, nothing upstream of the spec (epic/architecture/UI as team decisions). A team adopting bare Spec Kit still has to invent all the governance this repo provides.

Kiro (AWS) the polished product

What Amazon’s agentic IDE (Code OSS base, launched July 2025) built around specs: every feature gets requirements.md (EARS syntax) → design.md → tasks.md, plus automated hooks and steering files. Free tier; Pro $20 / Pro+ $40 / Power $200 per month.
Overlap The same spec-before-code conviction, productized with the smoothest UX in the market. Its three-file spec maps roughly onto this workflow’s epic → architecture → tasks chain.
Gaps vs this Single developer, single repo, single IDE — and a paid, closed product with AWS lock-in. The “gate” is one person clicking approve in their own editor; there is no team rule, no named-approval ledger, no contract shared across repos, no switchable automation with a recorded kill switch. Yadflow is IDE-agnostic (Claude Code, Codex CLI, Cursor, Gemini CLI, GitHub Copilot, Zencoder, opencode) and the state is portable files in git.

OpenSpec strongest at brownfield

What A lightweight open-source framework for spec-driven change on existing codebases: specs/ records current behaviour, each change is a self-contained package with delta specs (“what’s changing”), through a Propose → Validate → Apply → Archive state machine.
Overlap Its specs-for-what-exists idea parallels yad-backfill, and its change-isolation parallels the one-task-one-branch discipline. Reviewers in the market consistently rank it the best pure brownfield tool.
Gaps vs this Solo, single-repo, no human-approval machinery (validation is structural, not a team gate), no contract, no automation policy. Notably, its delta-spec approach is lighter than backfill — a fair criticism to absorb: Yadflow’s backfill requires packing and approving a feature spec before touching it, which is heavier but produces a human-verified record.

GSD (“Get Stuff Done”) the speed play

What A lean meta-prompting framework for Claude Code (~61,000 stars within five months of its Dec 2025 launch): one PLANNING prompt → prioritized TODO → one BUILDING loop until tests are green. Its focus is execution hygiene — keeping the agent’s context clean across a multi-task build.
Overlap Almost none in governance — but its explosive growth shows where the market’s center of gravity is: solo speed, minimal ceremony. It is the strongest argument against heavy process.
Gaps vs this Deliberately everything: no team, no gates, no contract, no audit trail. The right tool for a solo dev prototyping; the wrong one the day two repos and five engineers must agree on an API. The two aren’t really substitutes — but a small team will feel GSD’s pull.

Tessl the spec-as-source bet

What A language-agnostic “agent enablement” platform: installs as tiles in .tessl/, teaches any MCP-compatible agent a spec-driven workflow, and runs a Spec Registry of 10,000+ library specs to stop API hallucinations. Exploring “spec-as-source” — specs literally generating the code.
Overlap Shares the locked-truth instinct: its registry specs play a similar role to the locked contract — an agreed surface agents must not re-invent.
Gaps vs this Its locked truth is about third-party libraries, not your team’s cross-repo API. No review gates, no SDLC states, no automation governance. Different bet: Tessl thinks the spec replaces the code; this workflow thinks the team’s judgment stays the product.

Agent OS & Taskmaster AI workflow plumbing

What Agent OS (Builder Methods) standardizes multi-agent workflows and coding standards across different AI tools; Taskmaster AI decomposes a PRD into an executable task graph for agents.
Overlap Both formalize “plan → tasks → execute” like Build, and Agent OS shares the works-in-any-IDE stance.
Gaps vs this Both are solo orchestration layers: no human gates, no approvals, no contract, no run record. They answer “how do my agents stay organized?”, not “how does my team stay in control?”.

Enterprise platforms (Augment Cosmos, Microsoft’s agentic SDLC on Azure/GitHub) the from-above threat

What Platform-level offerings where agents run on shared context with telemetry, replayable sessions, and human-in-the-loop policies across the SDLC; Microsoft publishes a reference end-to-end agentic SDLC on Azure + GitHub.
Overlap They take governance as seriously as this workflow does — approval authority stays human, deterministic checks validate agent output. For a large enterprise, this is the budget-line competitor.
Gaps vs this Heavy, vendor-bound, and platform-priced; governance lives in their control plane, not in your git history. Yadflow’s counter-position is radical lightness: plain files, your repos, your CI, local-user auth, zero stored tokens, zero dashboard until measured need (the deliberately unbuilt Phase 5).

Adjacent, not competing: CodeRabbit, Graphite, Greptile the review slice

What AI code-review services that comment on PRs. They cover exactly one box of Build — the advisory AI review.
Overlap None to defend: Yadflow already uses CodeRabbit as its advisory pass and treats it as never-the-authority.
Gaps vs this They review diffs; they don’t govern a lifecycle. Complementary by design.

The honest scorecard — where competitors genuinely win

A deep analysis has to cut both ways. Where the market beats Yadflow today:
  • Ecosystem & trust-by-numbers: Spec Kit (~93k stars), GSD (~61k), BMAD (~46.7k) have communities, tutorials and hiring familiarity; this repo is effectively a single-maintainer npm package.
  • Product polish: Kiro is a real IDE with a UI; this workflow is markdown, JSON and CLI output. Teams that buy with their eyes will pick Kiro.
  • Ceremony cost: GSD and OpenSpec prove many teams want less process. For a 1–2 person project, this workflow’s six Shape reviews are overhead, not safety — its own docs effectively say so. Solo mode, the short chore/spike lanes and yad skip soften this, but do not remove it.
  • Dependency risk: the Build half leans on outside tools (Spec Kit, Repomix, CodeRabbit, the design and testing tools). Each is optional and degrades gracefully, but their conventions can change upstream.
  • No dashboards/analytics: deliberately (Phase 5 is trigger-gated), but enterprise buyers comparing against Cosmos-class platforms will count it as a gap.
